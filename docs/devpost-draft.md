## What it does (2-3 paragraphs)

Financial OS is a personal finance tracker that skips forms entirely. You type or speak — in English or Bahasa Indonesia — natural phrases like "spent 20 on coffee" or "bayar listrik 1.250.000". The parser understands intent, not just keywords: it rejects plans ("i want to buy a bike") and cancellations ("never mind that"), so your journal always reflects what actually happened.

The core innovation is the **Ethical Surplus** model. Most finance apps treat all remaining money as disposable. Financial OS calculates surplus only after obligations are covered — and never touches your principal savings. Users predict next week's surplus (Surplus Oracle), and when validated, can route 10% to a vetted cause via **PayPal Payouts** — with explicit two-step confirmation. No auto-donate, no dark patterns, no guilt tripping.

Everything is visual: journal, ledger with 36 filter combinations, PDF exports, Bryntum Gantt-powered long-term goal planning (Financial Horizon), and a scoped AI assistant that explains the app — but refuses general coding, off-topic questions, and jailbreaks.

## How we built it (2-3 paragraphs)

Backend is Fastify 4 + TypeScript on Render, connected to Neon Serverless Postgres, Upstash Redis, and Elastic Cloud. The natural-language parser is pure and deterministic (40/40 unit tests), handling USD and IDR formats, negation, and intent rejection. The PayPal Payouts integration uses a TypeScript SDK generated by **APIMatic** from PayPal's OpenAPI spec, running in sandbox mode.

Frontend is Next.js 14 App Router on Vercel, with server components for data fetching and a dedicated `/api/proxy` route for client-side calls — solving Next.js's strict `NEXT_PUBLIC_*` env boundary without leaking backend URLs. Design tokens follow a Stripe/Linear-inspired light palette with PayPal accent blue (#0070ba). Bryntum Gantt 8 Enterprise renders financial goals with custom fields (`targetAmount`, `monthlySaving`, `interestRate`, `loanTerm`).

The AI assistant is scoped by design: prompt embeds a versioned canary string; output is scanned before returning to the client (500 + alert on leak). Model is pinned: `google/gemini-3.8-flash` via OpenRouter, no aliases in env vars.

## Challenges (bullets)

- **Next.js client env boundary**: `process.env.API_URL` is undefined in client components. Solved with a generic proxy route that forwards to Render, zero CORS for the browser.
- **Render free-tier cold start** (~50s): Ledger auto-retries 3×4s and shows warm-up UX. Pre-warm before demo is mandatory.
- **Peer dependency mismatches**: `@fastify/cors@11` crashed Fastify 4 in production. Fixed by pinning v9 — rule added: check peer matrix before `pnpm add`.
- **Model ID normalization**: OpenRouter rejects model IDs without `provider/` prefix. Alias (`~`) gets stripped by env UI. Solution: pin explicit version in code, guard env var.

## What we learned (bullets)

- **"Model IDs need provider prefixes"**: env vars get sanitized. Pin in code, alias in env = broken.
- **"Auth check at session start ≠ auth mid-session"**: multi-account gh environments need verify-before-every-remote-op, not just at start.
- **"Peer dependencies are silent landmines"**: `pnpm add` without version pin on plugins with peer deps can crash production. Always check compatibility matrix.
- **"Cold start is a UX problem"**: 50s backend warm-up is fine for API tests, terrible for demo. Pre-warm must be a product feature, not a hope.
